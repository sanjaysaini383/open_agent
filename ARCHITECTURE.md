# ReliefMesh architecture

How the five sites, the official runtime and the response workflow fit together, and the
decisions behind them.

## Principles

1. **The specification and the official repository are the source of truth.** Every site
   follows the agentify-website conventions and passes the official scripts. The runtime is
   copied unchanged; nothing in it is patched.
2. **Sites are independent.** Each has its own origin, manifest, network, bridge, storage,
   runtime copy and tests. A site knows another only through that site's public files and
   the actions its bridge shares ([docs/INTEROP_CONTRACTS.md](docs/INTEROP_CONTRACTS.md)).
3. **Agents run in the browser.** There is no agent server and no backend.
4. **Numbers come from code, never from a model.** A model may explain a result.
5. **A person owns every commitment.** Consent before contact, approval before any write,
   confirmation in the owning site's own window.
6. **Say what is real.** Simulated data and real cross-origin calls are labelled apart.

Each site publishes, at its base:

| File | Purpose |
| --- | --- |
| `agent-manifest.json` | Networks, front agent, router metadata, peer policy, actions |
| `<network>.hocon` → `<network>.network.json` | The agent network; the JSON is generated by the official build |
| `links.json`, `agent-mcp.json`, `.well-known/` | Link map and discovery metadata (generated) |
| `site-actions.js` | The page's operations, offered to the site's own agents as `website_*` tools |
| `bridge/bridge-actions.js` | The actions shared with other sites; `bridge/action-bridge.html` is generated |
| `runtime/` | The official browser runtime, byte-identical to `vendor/agentify-website/runtime` |

The four partner sites are deliberately plain: HTML, CSS and ES modules, no build step, no
dependencies — the same shape as the official examples. Command is a React + TypeScript +
Vite application. Two different stacks interoperating through published files is the point.

## How Command uses the official runtime

`sites/command/public/` is Command's agent bundle. Vite copies `public/` into `dist/`
unchanged, so the runtime is never bundled or rewritten.

`src/interop/runtime.ts` loads `runtime/index.js` with a native dynamic `import()` and calls
its `boot()`, which mounts the chat in a container that lives **outside** the React tree
(`#agent-app` in `index.html`), so it stays mounted while pages change. Command then plugs
into the hooks the runtime offers:

| Runtime hook | Command supplies |
| --- | --- |
| `engine.onConsent` | The consent dialog: destination origin, purpose, calls, data sent |
| `engine.onActionConfirm` | The confirmation dialog; for plan approval, the full plan preview |
| `setActionWindowPrompt` | The "open the partner's own window" dialog |
| `trace` events | The activity panel, the live network graph and the developer trace |

The dashboard's app code cannot be imported by the plain `site-actions.js`, so the app
publishes one page object, `globalThis.__reliefmesh.page` (`src/workflow/page.ts`).
`site-actions.js` wraps its methods; the dashboard's own buttons call the same functions.

## One path for every cross-site call

`src/interop/peers.ts` is the only code that talks to a partner, and it does so only
through the runtime's engine:

```text
askConsent      engine.requestConsent     the runtime's gate; "allow for this session"
                                          is remembered in memory until reload
connect         engine.resolveRemote      allowed_peers policy -> manifest (exact network
                                          name) -> network validation -> bridge handshake
trust gate      TrustRegistry             record + signed attestation; signature verified
                                          with WebCrypto; digest of the published network
                                          file compared with the attested one
callRead        engine.actions            arguments validated against the PARTNER's schema;
                                          runs in a hidden frame on the partner's origin
callWrite       engine.actions            runs in the partner's own window, where the
                                          person confirms; receipt returned
parse           zod schema                a response that does not fit is rejected;
                                          instruction-like text is recorded, never obeyed
```

No data from a partner is used before the trust gate has passed. A blocked partner is
refused. An unverified one is refused unless a person explicitly allows it, which is
audited.

## Two execution modes over the same tools

| | Workflow | Agent console |
| --- | --- | --- |
| Driver | `src/workflow/steps.ts`, deterministic | The runtime's agent loop with the visitor's model |
| Needs a model key | No | Yes (the visitor's own) |
| Calls | The agent's tool directly | `website_*` tools, specialists, partner networks by URL |
| Labelled in the UI | *Direct tool* | *Model-driven* |

The published network gives `EmergencyCommanderAgent` nine specialists. Four of them name a
partner network URL in their `tools`; when a model picks one, the runtime shows consent,
loads the partner's network and runs **the partner's agents in this browser, on the
visitor's router and key**, with only the reads the partner's bridge shares.

The workflow attributes each step to the agent whose tool it runs, and says that no model
was called. That is an honest description of what happens, and it lets a judge run the whole
response without a key.

## The ten workflow steps

| # | Step | Agent | What runs | Partners contacted |
| --- | --- | --- | --- | --- |
| 1 | Create emergency | — (a person) | Validated form | — |
| 2 | Assess requirements | NeedAssessmentAgent | `domain/needs.ts` | TrustRegistry, ShelterConnect |
| 3 | Discover partner agents | DiscoveryAgent | `engine.resolveRemote` per partner | all four |
| 4 | Verify trust | TrustVerificationAgent | `domain/trust.ts`, `domain/crypto.ts` | TrustRegistry, AidSupply, RouteBridge |
| 5 | Collect supplier offers | SupplierMatchingAgent | `domain/offers.ts` | AidSupply, TrustRegistry |
| 6 | Negotiate | NegotiationAgent | `domain/negotiation.ts` | AidSupply |
| 7 | Optimise allocation | ResourceAllocationAgent | `domain/allocation.ts` | AidSupply (re-quotes) |
| 8 | Coordinate logistics | LogisticsAgent | `domain/logistics.ts` | RouteBridge, TrustRegistry |
| 9 | Human approval | — (a person) | `workflow/execution.ts` | — |
| 10 | Execute and track | — (a person), AuditAgent | `workflow/execution.ts` | AidSupply, RouteBridge, ShelterConnect |

RiskAnalysisAgent's tool (`domain/risk.ts`) runs after steps 5, 7 and 8.

Step 2 already needs ShelterConnect, before the discovery and trust steps. The trust gate is
therefore not a step but a property of `openPeer()`: a partner is verified the first time it
is used, wherever that happens.

## The allocation engine

`domain/allocation.ts`, deterministic and covered by 23 unit tests.

1. **Targets.** Per resource: if eligible supply covers demand, each shelter's target is its
   shortage. Otherwise supply is shared in proportion to `priorityScore × shortage`.
2. **Assignment.** Needs are served in global priority order. Candidate offers are ranked by
   `wCost × price/maxPrice + wTime × hours/maxHours + wTrust × (1 − trust/100)`, plus a fixed
   penalty for arriving after the deadline. Supply, budget and lane feasibility are hard limits.
3. **Minimum orders.** An offer below its minimum is raised to it by moving units from dearer
   suppliers; only if that is impossible is it dropped and the plan recomputed.
4. **Budget.** If the budget is what leaves need uncovered, cost-leaning weightings are tried
   and the plan covering the most units wins. The plan says when this happened.
5. **Validation.** `validateAllocation()` re-checks every invariant: no over-allocation, no
   over-ordering, no duplicates, minimum orders, budget, feasible lanes. A plan that fails is
   not shown.

Prices are tied to quantities. If the plan at quoted prices buys a different quantity from
an offer, that offer is quoted again; a quote that still does not match is withdrawn and the
list price is used.

Logistics feeds back. RouteBridge's route estimates replace Command's own; then the real
transport options (which include the time a vehicle needs to reach the pickup point) correct
any lane that would be late or unreachable, and the engine chooses again, at most twice.

## Trust

TrustRegistry signs attestations offline (ECDSA P-256 / SHA-256 over canonical JSON).
Command verifies them in the browser and scores transparent evidence
(`domain/trust.ts`): identity record, signature, integrity of the published network
definition, capabilities, credentials, reputation, open reports.

- The registry key is pinned on first use. A different key later blocks verification.
- A revoked or suspended record, a failed signature, or a published network that differs
  from the attested digest blocks, whatever the score.
- No record means *unverified*: never trusted.

The registry's **authority and credentials are simulated**. The **signatures are real**.

## The dashboard interface

Command's interface is a charcoal-teal glass command-centre by default (palette #2C3531, #116466, #D9B08C, #FFCB9A, #D1E8E2), with a whitish theme, built on
semantic design tokens (`src/index.css`: CSS variables for the default theme and
`html[data-theme="light"]`, exposed to Tailwind through `@theme inline`). Every component
is written once against those tokens. Motion uses Framer Motion and is short, eased and
optional: `prefers-reduced-motion` turns it off.

| Piece | Where | What it reads |
| --- | --- | --- |
| Shell: sidebar, header (incident selector, partner and agent status, model chip, alerts, theme, profile), command palette, keyboard shortcuts | `components/AppShell.tsx`, `CommandPalette.tsx`, `lib/shortcuts.ts`, `lib/nav.ts` | the store, `lib/theme.ts` (interface preferences, kept apart from demo data) |
| Alert centre | `lib/alerts.ts`, `components/AlertCenter.tsx` | derived from state at render time: unfulfilled demand, late or stuck shipments, unverified or blocked partners, failed requests, unknown write outcomes, pending approvals |
| Live agent network | `components/NetworkGraph.tsx` | the activity and interaction logs; a link exists only after a real request and carries particles only while one is in flight |
| Agent details panel | `components/AgentPanel.tsx` | the published network definitions (identity, capabilities, calls) and the activity log (task, status, history) |
| Live activity feed | `components/ActivityFeed.tsx` | activity, interactions, consent log and inbox, merged in time order |
| Scenario simulator | `pages/Simulator.tsx`, `workflow/scenarios.ts`, `workflow/simulation.ts` | creates a real incident and runs the real workflow; pause stops before the next step |
| Allocation editor | `pages/Allocation.tsx`, `workflow/editing.ts` | the engine's input rebuilt from the run; an edited plan passes `validateAllocation()` or is not stored |
| Approval Center | `pages/Approvals.tsx` | every item waiting for a person, with what, who asked, why and the consequences |
| Report | `pages/Report.tsx`, `lib/export.ts` | a print-styled page (the browser's "Save as PDF"), Markdown, JSON, CSV |

No metric, alert or feed entry is scripted. If the state holds no problem, the alert
centre is empty; if nothing has run, the feed is empty.

## State and static hosting

Every site keeps its state in its own origin's `localStorage`. A shared read runs in a frame
on the owning origin, and browsers partition a frame's storage by the top-level site.

- **Same registrable domain** (all `localhost` ports; subdomains of one domain): a site's
  page, its bridge frame and its confirmation window share storage. An edit on ShelterConnect
  is visible to Command's next read.
- **Different registrable domains** (separate `*.vercel.app` or `*.netlify.app` hosts): they
  do not. The bridge frame serves the published seed plus its own partition; a write confirmed
  in the owning site's window shows on that site's page, but not to the frame.

Command therefore keeps its own record of every receipt, subtracts its own reservations when
allocating, and never infers that a write happened from a later read. The official docs note
the same limit ("A site with no server keeps the change only in that window"). A production
deployment puts each site's state on that site's own server.

## Decisions

| Decision | Reason |
| --- | --- |
| Official runtime unmodified, loaded natively | Conformance. `npm run runtime:check` proves the copies are byte-identical. |
| Partner sites without a build step | Same shape as the official examples; nothing to compile before deploying. |
| No backend, no database | The specification needs none, and the demo must run anywhere. Persistence is browser storage. |
| Hash routing in Command | Any static host serves it with no rewrite rules, at a root or under a subpath. |
| Workflow runs tools directly | A judge can run everything without a key; numbers are reproducible. |
| Approval binds a digest of the plan | Execution refuses if the plan changed after it was reviewed. |
| One `openPeer()` for consent, policy and trust | A step cannot skip a gate by forgetting to call it. |
| Zustand for state, no component library | Small, explicit. The UI kit is `components/ui.tsx`; Framer Motion is the one animation dependency, and reduced motion is respected. |
| Interface preferences in their own store | Theme, sidebar and display name survive Reset demo and never mix with demonstration data. |
| PDF is the browser's print of a report view | No PDF library; the report page is print-styled and says so. |
| `.gitattributes` forces LF | Attested digests and runtime identity depend on exact bytes. |
