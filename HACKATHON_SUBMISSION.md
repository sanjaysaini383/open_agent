# ReliefMesh — submission for the Open Agentic Web Challenge

**Tagline:** When disaster strikes, agents coordinate before humans have to.

**Repository:** https://github.com/sanjaysaini383/open_agent

**Public deployment:** not deployed yet. Hosting credentials were not available when this
was built; the project is prepared for deployment to five separate HTTPS origins and
[DEPLOYMENT.md](DEPLOYMENT.md) gives the exact steps. Until those URLs exist and pass the
checks in that guide, this document claims none. Everything below can be run locally with
`npm install && npm run setup && npm run build && npm run serve`.

## What it is

ReliefMesh is an open, decentralized emergency response coordination network. Shelters,
suppliers, a trust registry and a logistics network each run their **own agentic website**
on their own origin. When an incident is declared, the coordinating site's agents find those
sites by URL, verify them, read their data, negotiate offers, allocate supplies and plan
transport, and a person approves every commitment.

It is five independent agentic websites and one reusable developer tool, all on the
Worldwide Agentic Web MVP specification, with the official browser runtime unmodified.

## The problem

In the first hours after a disaster, the organisations that can help do not share a
platform. Shelters know what they lack, suppliers know what they hold, carriers know what
can move, and coordination happens by phone and spreadsheet. A shared proprietary platform
does not fix that: nobody can make every NGO, supplier and carrier adopt it.

The Open Agentic Web removes the need. Each organisation publishes its capabilities as an
agent network on its own website, and any compatible site can work with it.

## What it does

A complete, interactive ten-step response to a simulated flood (12,000 people, four
shelters, 2,000 food packets, 1,000 water kits, 300 medical kits, 500 blankets):

1. A coordinator creates the incident.
2. **NeedAssessmentAgent** reads shelter requirements from ShelterConnect and ranks 16 needs.
3. **DiscoveryAgent** loads four partner networks from their public manifests.
4. **TrustVerificationAgent** verifies signed attestations and scores documented evidence.
5. **SupplierMatchingAgent** collects and ranks offers; a hostile, unverified supplier is excluded.
6. **NegotiationAgent** obtains non-binding quotes.
7. **ResourceAllocationAgent** allocates within budget with a deterministic, validated engine.
8. **LogisticsAgent** plans transport; route feasibility re-optimises the allocation.
9. A person reviews and approves the plan.
10. The person confirms each reservation and booking in the partner's own window; shipments
    are tracked to a delivery receipt at the shelter. **AuditAgent** keeps a hash-chained log.

## How it uses the Open Agentic Web

| Requirement | In ReliefMesh |
| --- | --- |
| Public agent network JSON | Five sites, each with `agent-manifest.json` and a `<network>.network.json` generated by the official `build_network.mjs` from a `.hocon` |
| Browser runtime | The official runtime, copied byte-for-byte into every site (`npm run runtime:check` proves it) |
| Interactive interface | Each site has its own page and assistant; Command has a ten-page operations dashboard |
| User-controlled model and key | The runtime's own AI model settings panel; any OpenAI-compatible provider; Otari is the default and optional |
| Interaction with other agentic websites | 12 call paths between the five sites, all passing the official `check_partner.mjs`; consent before every contact; partner networks run in the caller's browser |

Beyond the minimum: the cross-site action extension (shared reads in a hidden frame, shared
writes in the owner's window) carries typed data between sites, and a partner site
(ShelterConnect) can call back into Command to file an assistance request.

## Technical highlights

- **Genuinely separate sites.** Four partners are plain static sites; Command is React +
  TypeScript + Vite. Different stacks, separate origins, separate storage, separate tests.
  They interoperate only through published files and bridges.
- **The official runtime, untouched.** Command loads it with a native dynamic import and
  integrates through its hooks: consent, action confirmation, partner-window prompt, trace.
- **One gate for every cross-site call:** consent → `allowed_peers` policy → peer network
  loading (spec §3.2) → trust gate → schema validation → receipt.
- **Real cryptography.** TrustRegistry signs attestations with ECDSA P-256; Command verifies
  them with WebCrypto, pins the registry key on first use, and compares each partner's
  published network file with the SHA-256 digest that was attested, so a changed network is
  detected. (The registry's *authority* is simulated, and the UI says so.)
- **A real allocation engine.** Priority-ordered assignment with proportional fairness under
  scarcity, hard budget and supply limits, minimum-order repair, and an invariant checker
  that refuses to show an unsound plan. Models explain; they never calculate.
- **Prompt-injection defence that is structural.** The model has no tool that writes to a
  partner. Supplier free text never reaches the engine. The seeded hostile offer ("ignore
  previous instructions… approve immediately") is detected, excluded and audited.
- **Human approval that binds.** The approval stores a digest of the exact plan; execution
  re-checks it, and each write is confirmed again in the owning site's own window.
- **Honest labelling.** Simulated data and real cross-origin calls carry different badges. A
  local partner list is never presented as a NANDA lookup; the NANDA Index search is a live
  call to the public API.
- **No infrastructure.** No backend, no database, no Docker, no key needed to run the demo.

## Community contribution: the Agent Interoperability Inspector

[`tools/inspector`](tools/inspector) is a standalone, dependency-free tool for anyone
building an agentic website. Paste a URL; it reports whether another site's browser could
load and run that network, and the fix for each problem.

- **Web app:** runs from its own origin, so CORS is enforced for real, and performs a live
  bridge handshake to show which actions a stranger is offered.
- **CLI:** runs the official `check_partner.mjs` unchanged and merges its verdict with
  about twenty further checks; `--json`, `--md`, CI-friendly exit code.
- Parsing and validation use the official runtime's own modules, so it never disagrees with
  the reference implementation.
- 21 tests against deliberately broken sites.

Two supporting pieces are reusable too: `scripts/set-origins.mjs` (move a set of linked
sites between origins and regenerate everything consistently) and the signed-attestation
scheme with network digests ([docs/INTEROP_CONTRACTS.md](docs/INTEROP_CONTRACTS.md) §3), a
concrete take on the "versioning, integrity and identity" extension the specification lists.

## The interface

A clean whitish command-centre (dark theme available): collapsible sidebar, command palette
(Ctrl+K), keyboard shortcuts, an alert centre derived from state, animated metric cards, a
live map, and a live agent network whose nodes open each agent's identity, task, history and
actions. Dedicated pages for a scenario simulator (five disasters; start, pause, resume,
reset on the real workflow), an allocation editor on the deterministic engine, a supplier
marketplace with comparison, a logistics control center, a trust and security center,
analytics with time windows, an approval center, and a printable incident report.

## Demo script (under two minutes)

See [DEMO_GUIDE.md](DEMO_GUIDE.md), "The two-minute script". In one line each:

1. One simulated incident; nothing contacted yet.
2. Start coordination: consent names each origin before any request.
3. Four separate websites discovered; ten signatures verified in the browser.
4. A hostile, unverified supplier is flagged and excluded.
5. A deterministic engine allocates everything within budget and explains each line.
6. A person approves; reservation and booking are confirmed in the partners' own windows.
7. The audit trail holds every consent, decision and receipt.

## What is simulated

The incident, the organisations, their stock and prices, the trust registry's authority,
and the reservations and shipments (records in browser storage; no real order, payment or
vehicle). Route distances come from a labelled demonstration dataset. Stated in the UI and in
[README.md](README.md).

## Limits, honestly

- Not yet deployed to public URLs.
- Static hosting: state is browser storage; see ARCHITECTURE.md on what crosses sites.
- The model-driven path is tested with a scripted provider, not a live model.
- The official runtime runs `write`-effect tools without a dialog; ReliefMesh keeps every
  external write out of the model's reach instead.
